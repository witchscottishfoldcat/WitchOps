# Witchcat Ops 功能闭环优化计划

编制日期：2026-09-12
审查基线：本地仓库 HEAD `dd38209`。本计划基于源码、数据库迁移、IPC 与现有设计文档的静态核对；没有连接真实服务器、调用模型、运行构建或执行端到端测试。下文“现状”是代码证据，“目标”与工期是实施建议。

## 1. 目标与范围

保留 Tauri + React + Rust + SQLite 的单机桌面架构，将已有运维模块串成可验证、可恢复、可复用的工作流程：

```text
选定服务器 / 发现异常
  → 创建运维任务，记录现象、目标与验收条件
  → 采集证据，匹配已审核 SOP
  → 生成操作方案、风险说明、验证与回退方案
  → 人工审批不可变的操作内容
  → 执行并持久化每一步状态、输出与审计关联
  → 验证目标是否达到
      ├─ 通过：结案 → 生成有证据的复盘 → 人工审核 → 发布 SOP
      └─ 未通过 / 结果未知：保留现场 → 诊断或批准回退 → 再验证
  → 后续同类任务引用 SOP，记录实际效果
```

闭环完成的标准：用户能回答“处理什么问题、在哪台机器、批准了什么、实际发生什么、问题是否解决、失败如何处理、下次如何复用”。命令退出码为 0 仅代表命令执行成功，不等于故障解决。

首版范围：单用户、Windows 桌面客户端、Linux SSH 目标、单服务器任务。沿用已有人工批准写操作的交互。多服务器事务、团队权限、全天候后台监控和 MCP 扩展放到主链路验收之后。应用关闭期间不承诺持续监控。

## 2. 当前已有基础与实际断点

已有基础：服务器与主机指纹管理、SSH/PTY/SFTP、监控、Docker/Systemd、Vault、服务端 Agent 提案审批、审计查询、会话 JSONL、文档和技能 CRUD。优先复用这些能力，逐步补齐执行编排与结果验证。

| 优先级 | 代码确认的现状 | 对闭环的影响 | 代码位置 |
| --- | --- | --- | --- |
| P0 | 提案在实际执行前由 `approved` 改为 `executed`，未持久化 running/failed/unknown 等执行结果状态 | 断线、进程退出或执行失败后，无法从提案状态判断真实结果 | `src-tauri/src/commands/proposals.rs::execute_agent_proposal`，`migrations/0002_agent_proposals.sql` |
| P0 | 快捷指令检查 guard 的 `success`，但普通步骤只 await，不检查返回的 `success` | 中间命令非零退出后仍可能继续后续变更 | `src/context/AppContext.tsx::executeQuickActionSteps` |
| P0 | 执行器先远程执行、再插入审计；部分 SFTP 操作审计失败只写 warning | 已执行但本地证据缺失，重试容易误操作 | `src-tauri/src/executor.rs::execute_and_audit`，`commands/sftp.rs::audit_sftp_action` |

| P0 | 通用执行接口仅拦截 `ctx.source == "agent"`，其他 source 和 approved_by 仍由前端提供 | 服务端审批约束仅覆盖专用提案入口，不能声称渲染进程被攻破后仍无法绕过 | `src-tauri/src/commands/servers.rs::execute_command` |
| P1 | Agent 分发只取 `turn.toolCalls[0]`；写提案只提示剩余调用被丢弃 | 多工具、多步骤分析无法完整执行 | `src/components/AgentChatPanel.tsx::dispatchToolCalls` |
| P1 | 会话恢复仅重建纯文本，工具调用与结果配对无法恢复；审批 UI 先更新后请求后端，拒绝失败仍更新 UI | 重启后推理上下文不全，显示状态与数据库可能不同 | `src/lib/agent.ts::restoreHistory`，`AgentChatPanel.tsx::handleApprove/handleReject` |
| P1 | 保存复盘只是拼接对话，`session_id: null`；未汇总关联审计与验证证据 | 文档不能可靠追溯操作过程，也不能证明问题已解决 | `src/components/AgentChatPanel.tsx::handleSaveAsDoc` |
| P1 | 文档转技能直接复制正文，默认低风险且启用；未校验 reviewed；冲突更新用 `excluded.version + 1`，该入口插入版本恒为 1 | 草稿可能直接反哺 Agent，重复转换版本停在 2 | `src-tauri/src/commands/knowledge.rs::doc_to_skill` |
| P1 | 技能上下文仅使用 id/title；虽加载 triggers，但提示未使用；未带入 applies_to 与目标标签 | 缺少明确的适用性匹配、版本引用和复用效果记录 | `src/lib/agent.ts::loadEnabledSkills/systemPrompt` |
| P1 | 仪表盘为当前数值轮询，缺少告警实例、处理任务和恢复确认；轮询失败只记日志 | 发现异常与处理结果没有产品链路，旧数据可能持续显示 | `src/context/AppContext.tsx::refreshMetrics`，`MetricsDashboard.tsx` |
| P1 | 审计页面只过滤已加载日志；后端已有筛选及分页 SQL；页面宣称完整输出，但执行器只存约 2000 字节摘要 | 搜索范围不完整，展示承诺与证据保存不一致 | `AuditLogs.tsx`，`commands/knowledge.rs::query_audit_logs`，`executor.rs` |
| P1 | 默认数据目录来自编译期源码路径；Cargo target-dir 硬编码旧用户名；旧库迁移忽略复制错误且仅搬数据库文件 | 换机安装、升级与恢复缺少可靠路径，会话也可能未迁移 | `src-tauri/src/lib.rs`，`src-tauri/.cargo/config.toml` |

补充边界：监控等只读采集存在直接调用 `ssh.run_command` 的路径，PTY 也不等价于普通命令执行。应明确“变更审计、任务诊断证据、后台采样、终端会话记录”四种记录语义；不必将每次 5 秒监控采样都写成一条变更审计。

## 3. 建立共同的任务与执行模型

增加轻量“运维任务”，连接现有页面，无需建设复杂工单系统。任务详情展示：目标服务器、问题与验收条件、诊断证据、待批准步骤、执行进度、验证结果、恢复入口、关联文档与 SOP。

建议新增数据模型，具体迁移编号在实施时按仓库最新状态追加：

| 模型 | 最小内容 | 用途 |
| --- | --- | --- |
| `ops_tasks` | id、server_id、标题、触发来源、目标、验收条件、状态、创建/关闭时间 | 统一业务目标与结案状态 |
| `operation_runs` | id、task_id、来源、源对象版本、目标快照、审批内容哈希、状态、开始/结束时间 | 一次操作的持久化身份与去重基础 |
| `operation_steps` | run_id、顺序、类型、输入快照、状态、退出码、错误、超时、audit_id、输出引用 | 逐步执行与恢复，不依赖 React 组件生命周期 |
| `verification_results` | task_id/run_id、断言、实际值、证据引用、pass/fail/unknown、时间 | 将执行成功与目标达成分开 |
| `agent_events` | session_id、递增序号、事件类型、完整 tool_call_id/结果/提案关联 | 可重放的结构化会话，防止工具上下文丢失 |
| `skill_revisions` / `skill_usages` | 技能版本快照、审核状态、来源文档、引用任务、验证结果、反馈 | 发布与效果追踪 |

现有 proposals/audit/docs 增加 task_id/run_id 等必要关联；新增的验证操作也进入步骤与审计体系。原始记录保留，删除服务器或会话不连带删除已发生的审计事实。

状态设计：

- 提案：`pending → approved / rejected / expired`。内容或目标改变后生成新提案，原审批失效。
- 执行：`queued → running → succeeded / failed / cancelled / unknown`。原子领取 `queued → running`，防止并发重复启动。
- 任务：`open → diagnosing → awaiting_approval → executing → verifying → resolved`；失败转 `needs_attention`，回退有独立执行记录，随后重新验证。用户可取消任务并填写原因。
- 文档：沿用 `draft → reviewed → archived`。技能单独使用草稿、已发布、停用的生命周期。

服务端为执行状态的唯一事实来源，前端事件用于及时展示，重连/切页后通过查询校准。单机 SQLite 事务不能保证远程 SSH 命令 exactly-once：发出命令后丢失连接，应标为 unknown，禁止自动重放有副作用的命令。

## 4. 分阶段实施

### M0：修复会误导用户或导致继续误操作的问题（P0，约 4–6 人日）

1. 快捷指令每个普通步骤检查退出码；默认失败立即停止，剩余步骤显示 skipped。guard 失败返回明确失败状态，不将正常 return 当作流程成功。未支持的步骤类型应在执行前报错，不能静默跳过。
2. 提案保留原子防重，先引入 running/failed/unknown 等实际执行状态及结果关联；后续 M1 将其归并到通用 run 模型。审批按钮显示 submitting，收到后端结果后更新；失败重新读取状态。
3. 执行前落库运行意图，数据库写入失败则不发送变更命令；执行后补充结果。收尾写库失败保留“结果待核对”，UI 明示命令可能已执行，不提供无条件重试。
4. 修正 PTY 审计：输入、命令结果和会话结束分别表达。无法证明逐命令结果时记录 unknown/input_recorded，不能记为成功。先停止默认保存原始输入行，保留连接/会话元数据；如以后启用终端录制，应明确覆盖范围、加密和访问控制。不能依赖密码正则可靠识别交互输入。
5. 凭证和执行参数引入统一脱敏策略，覆盖审计、诊断日志、Agent 上下文、文档导出。Vault 已有启用后迁移明文凭证的逻辑，应验证部分失败可恢复；首次保存敏感凭证时引导启用 Vault，显示实际存储状态。
6. 通用手动命令入口由后端构造 source/approved_by，校验可用来源；快捷操作逐步改为提交操作 ID 与服务端快照，不接受前端任意声明“已审批”。明确本地可信 UI 的安全边界，移除“完全免疫绕过”式承诺。

主要落点：`executor.rs`、`commands/proposals.rs`、`commands/servers.rs`、`commands/sftp.rs`、`terminal.rs`、`AppContext.tsx`、`AgentChatPanel.tsx`、新增迁移。

验收门槛：重复点击只执行一次；第 2 步失败时第 3 步不启动；断线不显示成功；审计库不可写时拒绝新的变更；密码输入不会默认写入审计；前后端审批状态一致。

### M1：后端持久执行与任务结果闭环（P1，约 7–10 人日）

1. 落地任务、run、step、verification 模型与 IPC。将快捷指令步骤编排移到 Rust 服务，前端订阅进度；页面切换不影响运行。
2. 逐步统一 Agent、快捷指令、容器/服务控制、SFTP 写操作的执行记录。PTY 保持交互式会话语义，可关联任务，但不假装能准确解析所有 shell 操作。
3. 固定审批快照：目标主机与指纹、命令/文件差异、步骤顺序、风险、验证与回退方案。批准后不重新读取可变快捷指令内容进行执行。
4. 支持 precheck、execute、verify 和显式 rollback 步骤。捕获变量只开放声明过的字段；定义目标绑定、类型校验、引用方式与转义规则，未支持的 capture/target/approval 选项从 UI 隐藏或明确拒绝。
5. 设定单步超时、输出上限、单主机变更并发上限。取消先停止调度后续步骤；是否终止远程进程依工具能力决定，未确认停止不能标 cancelled。
6. 写文件提供内容 diff、可恢复的原文件备份、临时文件写入与适用时的原子替换；执行前检测文件是否已被他人修改。重试和回退都产生新 run，并保留原执行关系。
7. 每次变更都有验证断言。例如重启服务后检查 active、端口和 HTTP 健康；磁盘治理后重新测量指定挂载点。缺少证据显示待验证。人工结案需注明理由，不覆盖失败证据。

建议新增 `src-tauri/src/operations/` 与 `commands/tasks.rs`、`commands/runs.rs`；前端新增任务详情和执行进度组件。`AppContext` 按服务器、Agent、任务、知识分域拆分，跟随功能迁移进行，避免一次性重写。

验收门槛：手动创建“服务异常”任务 → 诊断 → 审批 → 修复 → 健康检查 → resolved 全流程可查；应用重启可找回 running/unknown 任务；失败或未知结果不会自动重试变更；回退能查到独立结果。

### M2：Agent 多步执行与历史恢复（P1，约 5–8 人日）

1. 将 Agent 工具调用统一接入任务/run；只读工具使用明确的工具能力策略，`safe_to_run` 仅作模型建议，不承担授权判断。
2. 持久化完整 assistant/tool_calls/tool 结构与会话模型配置；一个调用对应一个明确结果。支持调用队列：首版顺序执行，多条写操作按批准范围逐步处理，不再丢弃第 2 条及之后的调用。
3. 用户拒绝、工具失败、取消都形成结构化事件，反馈给 Agent 解释或重新规划。对于不支持的工具与强制审核的只读调用，走明确的错误/审批分支，避免落入未知写工具分支。
4. 增加单任务轮次、工具调用数、时长与上下文预算，达到上限暂停并保留状态。取消覆盖模型请求、只读续轮和待启动工具；已在远程执行的变更遵循 M1 语义。
5. JSONL 旧会话可保留只读历史；新结构化事件以数据库为事实来源，避免两个存储同时充当主数据。无法恢复的历史工具状态显示缺失，不推测补全。
6. Provider/model 可显式选择并绑定会话，增加连接测试、模型失败/超时/Vault 锁定提示。请求中切换服务器或会话时，执行目标仍以批准快照为准。

主要落点：`src/lib/agent.ts`、`AgentChatPanel.tsx`、`AgentMemory.tsx`、`commands/agent_chat.rs`、`commands/sessions.rs`、`commands/providers.rs`、`SettingsManager.tsx`。

验收门槛：同轮 3 个工具全部有结果；重启恢复后模型能取得原 tool_call 与结果；拒绝提案后可以继续讨论替代方案；达到预算自动暂停；切换页面或会话不会将结果挂错目标。

### M3：审计 → 复盘 → SOP → 再使用（P1，约 5–8 人日）

1. 任务结束后提供“生成复盘草稿”，输入为任务目标、实际审计、前后指标、验证结果、失败/回退和会话摘要；保存真实 task_id/session_id/server_id。
2. 先使用确定性模板列出时间线与证据，再由 LLM 总结；没有 Provider 时仍可生成基础文档。根因缺乏证据时写“待确认”，明确区分观察与推断。
3. 审计正文存摘要，按需保存有大小/保留期限制的加密输出附件；展示截断标识。文档引用 audit_id/step_id，不默认将完整远程文件、秘密和终端输入发送给模型。
4. 文档审核后才能转为技能草稿；SOP 要求前置条件、适用系统/标签、参数、风险、步骤、成功判据、回退方式。发布前人工审核，默认不自动启用。
5. 修复版本递增，保存不可变技能版本。根据任务目标、triggers、服务器 tags/applies_to 推荐技能，显示匹配依据；首版采用确定性匹配，无需引入向量数据库。
6. 记录每次任务引用的 skill_id/version、验证结果和人工评价；区分“使用了技能”与“技能有效”，失败案例回流到修订草稿，停用旧版本不删除历史引用。
7. 审计筛选接后端分页/搜索，提供 task/session/run 跳转，刷新由统一事件驱动。修正“完整 stdout/stderr”“全部日志”等与实现不符的文案。

主要落点：`commands/knowledge.rs`、`DocsHub.tsx`、`SkillsManager.tsx`、`AuditLogs.tsx`、`AgentChatPanel.tsx`、`agent.ts`。

验收门槛：从真实任务生成带审计引用的复盘 → reviewed → 技能草稿 → 发布 v1 → 第二个任务推荐并引用 v1 → 验证与反馈；重复修订到 v3 后版本与历史正确；未审核文档不能直接变成启用技能。

### M4：发现异常与基础运维体验连通（P1/P2，约 4–6 人日）

1. 监控增加采样时间、陈旧状态、短期趋势、失败次数和退避；避免同一服务器请求重叠，页面/连接切换隔离旧响应，后台采样按需要降频。
2. 在应用运行期间支持磁盘、内存、CPU 持续阈值规则，定义连续触发窗口、去重键、恢复阈值及冷却时间。新增轻量告警规则/实例持久化，不因每次采样创建重复任务。
3. 异常卡片“一键诊断”创建任务并带入指标快照；处理后复测，告警恢复与任务结案有明确关联。告警仅触发诊断，不直接执行变更。
4. 服务/容器入口显示前置能力检查、日志与操作后验证；SFTP 上传下载补充进度、取消结果、覆盖冲突、大小/完整性核对。优先补实际失败处理，再考虑断点续传。
5. 首次使用串联 Vault、服务器、主机指纹、连接检测、只读诊断与可选 Provider 配置；统一未连接、加载、错误、空数据状态。暂时移除或禁用未实现的全局搜索入口。

验收门槛：模拟磁盘持续越阈值只形成一个活动告警 → 创建诊断任务 → 审批处理 → 复测恢复；断线显示数据已过期；无 Docker/Systemd 时给出明确不可用状态；首次用户能完成一次只读诊断。

### M5：可安装、可升级、可备份恢复（P1，约 4–6 人日）

1. 发布版默认使用运行时应用数据目录；保留 `WITCHCAT_DATA_DIR` 显式覆盖，开发模式可单独配置。移除版本库中带用户名的 Cargo 输出目录，提供本地覆盖说明。
2. 数据迁移覆盖 SQLite、会话与输出附件，错误必须可见；在一致性快照或停写条件下迁移，完成校验后才切换目录。原数据保留到确认成功。
3. 数据库增量迁移记录与 schema 更新保证一致；升级前快照，迁移失败可恢复。旧库升级测试包括部分失败、重复启动及历史外键关联。
4. 实现加密备份/恢复：包含 schema/应用版本、数据库一致性快照、附件、会话与清单校验；不能只复制正在写入的 app.db。恢复先在临时目录验证，再切换，保留现有库备份。
5. 在无原机钥匙串的新环境验证：使用备份和 Vault 主密码仍能解密凭证；钥匙串恢复只能作为同机便利路径。文件缺失或密码错误不能破坏现有数据。
6. 建立前端构建、Rust 单测与关键集成测试的持续检查；添加 Windows 安装/启动冒烟测试。同步 README、IPC 契约与功能说明，例如 LLM 已经走后端代理，不能继续写前端直连。

验收门槛：新 Windows 用户环境可安装启动；旧库升级成功；备份恢复后服务器、凭证、会话、审计、文档、技能和版本引用完整；损坏备份被拒绝且原数据不受影响。

## 5. 验收用例与发布门槛

使用隔离 Linux 测试机或容器环境，避免在真实业务服务器演练破坏性操作。已有 Rust 局部测试可复用；仓库目前没有前端 test 脚本，需补关键业务测试入口，而非只测试组件是否渲染。

| 编号 | 场景 | 必须得到的结果 |
| --- | --- | --- |
| A1 | 正常服务修复 | 问题 → 审批 → 执行 → 服务/端口/健康验证 → resolved，全部证据相连 |
| A2 | 快捷指令中间步骤退出 1 | 当前步 failed，后续变更 skipped，任务 needs_attention |
| A3 | 审批双击/并发提交 | 相同执行 ID 只启动一次，重复请求可查询已有执行结果 |
| A4 | 命令发出后断网或退出应用 | 重启显示 unknown/待核对，不自动重发变更 |
| A5 | 数据库写入失败 | 执行前失败阻止变更；执行后失败清晰说明结果待核对 |
| A6 | 审批后修改快捷指令/切换服务器 | 已批准内容与目标不变；新内容要求新审批 |
| A7 | 同轮多个工具与拒绝操作 | 每个调用有结果/拒绝状态；模型续轮上下文合法、可恢复 |
| A8 | 命令成功但业务验证失败 | 不结案，保留断言结果并进入诊断/回退流程 |
| A9 | 写配置后健康检查失败 | 展示备份与回退方案，批准回退后再次验证 |
| A10 | 复盘发布和技能再用 | 所有结论可追溯证据；v1/v2/v3 可追踪，未审核技能不启用 |
| A11 | 终端输入 sudo 密码/输出含令牌 | 默认审计、日志、模型请求和文档不泄漏测试秘密 |
| A12 | 审计量超过一页 | 后端筛选覆盖完整记录集，分页稳定，任务跳转准确 |
| A13 | 告警持续与恢复 | 无重复活动告警，修复后复测可关闭，旧采样不冒充新数据 |
| A14 | 换机与旧库升级/备份恢复 | 无开发机绝对路径依赖，数据完整，错误可恢复 |

核心发布门槛：A1–A12 和 A14 全部通过；启用告警时 A13 必须通过。测试中不得出现未批准变更、同一 run 重复启动、unknown 被标为成功、失败后继续变更或秘密泄漏。每个已关闭任务都应具备验证证据或明确的人工结案理由。

质量指标先记录基线，再设置服务目标：任务验证通过率、unknown 数量及处理时长、审计结果补写失败数、复盘审核率、SOP 再使用后的验证通过率。不把“命令成功次数”当作产品闭环指标。

## 6. 执行顺序、估算与暂缓项

依赖顺序：`M0 → M1 → M2 → M3`；M4 依赖 M1 的任务/验证能力；M5 中的路径与构建检查从 M0 开始，最终恢复验收在数据模型稳定后完成。

按一名熟悉 React/Rust 的开发者估算：M0–M5 合计约 29–44 人日，另预留约 20% 联调缓冲。约 7–11 个工作周，属于静态评估，不是交付承诺；M0 完成并跑通构建后重新估算。若先交付核心闭环，可先上线 M0–M3 加 M5 必要发布保障，告警与体验扩展随后进入。

建议第一批变更拆成可独立审查的小提交：

1. 快捷指令失败即停止，补一个三步骤失败用例。
2. 提案 running/failed/unknown 状态与前端真实状态回读。
3. 执行前记录与审计写入失败语义统一。
4. PTY 审计语义和秘密输入保护。
5. 通用执行入口由服务端构造来源/审批信息。
6. 数据路径和构建配置可迁移；建立构建/测试基线。

暂缓：MCP Server/Client、多主机批量变更、无人值守自动修复、团队 RBAC、向量检索、终端分屏和进一步主题扩展。启用 MCP 前先完成同一执行策略、状态恢复与审计协议，避免新增一套旁路。

本计划交付的是优化路线与验收标准。实施优先从 M0 开始，每一阶段以可演示的成功与失败场景验收，避免只按页面或接口数量判断完成度。

## 7. 实施进度

2026-09-13 已完成首批 M0 改造，并提前落地部分 M3/M5 能力：快捷指令迁到后端按预览版本执行并在任一步失败时停止；Agent 提案持久化 running/succeeded/failed/unknown，启动时把中断状态转为 unknown；命令和 SFTP 写操作改为先登记审计再执行；审计区分 pending/failed/unknown；PTY 默认不再记录可能包含密码的输入行；移除接受前端自报 source/approved_by 的通用命令 IPC。Agent 复盘草稿关联真实 session_id 和审计证据，文档只有 reviewed 后才能转为默认停用的技能草稿，并修正技能版本递增，技能上下文增加适用范围、触发词、风险和版本。发布版默认使用系统应用数据目录，首次启动安全备份后导入旧项目数据；Cargo 配置移除旧用户名绝对路径。前端生产构建、34 个 Rust 测试和 Windows MSI/NSIS 整包构建均已通过。
